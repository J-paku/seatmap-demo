# 03-pitfalls — 함정 사례집 (누적형)

작업 중 "이거 어디서 본 문제인데" 싶을 때, 또는 새로운 사고가 발생해 항목을 추가할 때 읽고 쓴다. 이 문서는 매 사고마다 항목이 늘어나는 **누적형**이며, 기존 항목을 지우지 않는다.

## 항목 템플릿

새 항목을 추가할 때 이 형식을 그대로 따른다. 필드를 생략하지 않는다.

```
### N. 제목 (한 줄로 사고를 요약)

**증상**: 무엇이 어떻게 잘못 보였는가
**원인**: 근본 원인 (표면적 증상이 아니라 왜 그 증상이 나왔는가)

**회피법**: 다음에 같은 상황을 만나면 무엇을 확인해야 하는가 (결정 가능한 절차로)
**발견 경위**: YYYY-MM-DD, 발견 상황 한 줄
```

### 1. 빌드 도구의 자동 벤더 프리픽싱과 수동 작성의 충돌

**증상**: 소스 CSS에는 `backdrop-filter` 효과가 정상적으로 정의되어 있는데, 실제 배포된 화면에서는 블러 효과가 전혀 적용되지 않았다.

**원인**: Lightning CSS 계열 빌드 도구는 표준 프로퍼티만 작성해도 자동으로 `-webkit-` 프리픽스와 표준 선언 양쪽을 생성한다. 그런데 소스에 표준 선언과 `-webkit-` 선언을 **양쪽 다 손으로** 적어두면, 빌드 도구가 이를 "이미 프리픽스 처리된 블록"으로 오인해 표준 선언을 산출물에서 누락시킨다. 결과적으로 산출물에는 `-webkit-backdrop-filter` 만 남는데, 최신 Chromium은 이 구식 프리픽스를 더 이상 지원하지 않아 효과가 죽는다.

**왜 코드 리뷰로 못 잡는가**: 소스 코드만 보면 표준 프로퍼티와 프리픽스 프로퍼티가 나란히 있어 오히려 "꼼꼼하게 작성했다"는 인상을 준다. 문제는 컴파일 단계에서만 발생하므로 산출물을 직접 열어보지 않는 한 절대 드러나지 않는다.

**회피법**: CSS에서 벤더 프리픽스(`-webkit-`, `-moz-` 등)를 손으로 쓰지 않는다. 표준 프로퍼티만 작성하고 빌드 도구의 자동 프리픽싱에 맡긴다. 프리픽스가 실제로 필요한지 의심되면 빌드 산출물의 CSS 파일을 직접 열어 대상 프로퍼티가 어떤 형태로 나갔는지 확인한다. 관련 원칙: [02-verifying.md#2-컴파일-결과를-봐야-하는-부류](./02-verifying.md#2-컴파일-결과를-봐야-하는-부류).

**발견 경위**: 2026-07-31, 배포 후 블러 효과가 실기기에서만 사라지는 것을 발견해 산출물 CSS를 직접 열어본 세션.

### 2. 무효화 수단 없는 클라이언트 캐시

**증상**: 특정 사용자의 브라우저에서만 팀 전체 인원수가 `0` 으로 표시되었다. 새 브라우저·시크릿 창에서는 재현되지 않았다.

**원인**: 목 데이터를 `localStorage`에 캐시하면서 버전 정보나 데이터 지문(fingerprint)을 함께 저장하지 않았다. 이후 배포에서 좌석 id 체계가 `seat-001` 형식에서 `dept-sales-001` 형식으로 바뀌었는데, 이미 옛 캐시가 저장된 브라우저는 새 코드가 옛 스키마의 데이터를 그대로 읽어 들여 매칭에 실패했다. 브라우저 강제 새로고침(하드 리로드)으로도 `localStorage`는 지워지지 않는다.

**왜 코드 리뷰로 못 잡는가**: 새 스키마로 작성된 코드 자체는 정상이다. 문제는 "이전에 이미 저장된 상태"와 "새 코드"의 조합에서만 발생하므로, 새 브라우저·새 세션에서 아무리 테스트해도 재현되지 않는다. 개발자는 항상 깨끗한 환경에서 작업하기 때문에 이 부류의 버그를 구조적으로 놓친다.

**회피법**: 클라이언트 측에 데이터를 캐시할 때는 항상 버전·스키마 지문을 캐시 키 또는 캐시 값에 포함시켜, 스키마 변경 시 자동으로 무효화되게 한다. 검증 시에는 새 브라우저가 아니라 **구버전 상태를 실제로 만든 브라우저**에서 재시도한다. 관련 원칙: [02-verifying.md#3-개발자-환경에서-재현-안-되는-부류](./02-verifying.md#3-개발자-환경에서-재현-안-되는-부류).

**발견 경위**: 2026-07-31, 특정 사용자 환경에서만 재현되는 버그를 조사하며 `localStorage` 내용을 직접 확인한 세션.

### 3. `ResizeObserver` 의 최초 통지에 의존하는 코드

**증상**: 저사양·부하 환경에서 레이아웃 계산이 간헐적으로 누락되거나 잘못된 크기로 확정되었다. 일반 환경에서는 재현되지 않았다.

**원인**: 두 가지가 겹친 문제였다. 첫째, `ResizeObserver.observe()`는 실제 크기 변화가 없어도 최초 1회 통지를 보장하는데, 이 통지가 "다른 effect가 유발한 리렌더 뒤에 도착한다"는 순서를 코드가 암묵적으로 가정하고 있었다. 그러나 이 도착 순서는 React 스케줄러의 명세되지 않은 동작이라 부하 환경에서 뒤집힐 수 있다. 둘째, `width: 100%`인 블록 컨테이너는 내부 콘텐츠가 넘쳐도 **자기 박스 자체는 커지지 않으므로**, 관찰 대상으로 지정해도 리사이즈 통지 자체가 오지 않는 경우가 있었다(`min-width: auto` 해제는 그리드·플렉스 아이템에만 적용되고 일반 블록 컨테이너에는 적용되지 않는다).

**왜 코드 리뷰로 못 잡는가**: 리뷰 시점에는 "리렌더 뒤에 통지가 온다"는 가정이 일반 환경에서는 대체로 성립하기 때문에 정상 동작처럼 보인다. 스케줄러의 타이밍은 코드에 텍스트로 드러나지 않는 명세되지 않은 동작이라, 소스만 봐서는 이 가정이 존재한다는 사실 자체를 알아채기 어렵다.

**회피법**: `ResizeObserver`의 통지 순서를 다른 effect의 실행 순서에 대한 암묵적 의존으로 사용하지 않는다. 관찰 대상을 추가하기 전에, 그 요소가 실제로 리사이즈되는 요소인지(자기 박스가 콘텐츠에 따라 변하는지) 먼저 확인한다. `width: 100%` 블록 컨테이너처럼 자체 크기가 고정된 요소를 관찰 대상으로 잡고 있다면, 실제로 크기가 변하는 자식이나 부모를 관찰 대상으로 바꾼다.

**발견 경위**: 2026-07-31, 저사양 환경 재현 테스트 중 레이아웃 계산 누락을 발견한 세션.

### 4. 동일 개념의 두 번째 판정 기준

**증상**: 데이터 스키마 변경 후, 같은 "팀 소속" 개념을 다루는 두 곳 중 한쪽만 깨졌다.

**원인**: 동일한 소속 관계를 판정하는 기준이 코드베이스 안에 두 가지로 존재했다. 한 곳은 `id` 문자열의 접두사(`dept-sales-`)로 소속을 판정했고, 다른 곳은 별도의 `teamId` 필드로 판정했다. 두 기준은 원래 항상 같은 결과를 냈기 때문에 아무도 이것이 "두 개의 진실 소스"라는 것을 인지하지 못했다. 데이터 스키마가 바뀌면서 `id` 접두사 규칙만 변경되고 `teamId` 필드는 그대로 유지되자, 접두사로 판정하던 쪽만 깨졌다.

**왜 코드 리뷰로 못 잡는가**: 각 판정 로직은 개별적으로 보면 정상적으로 동작하는 코드다. 문제는 "같은 개념을 서로 다른 방식으로 두 번 판정하고 있다"는 사실이 코드베이스 전체를 가로질러야만 보이는데, 통상의 파일 단위 리뷰는 이 교차 검증을 하지 않는다.

**회피법**: 같은 개념(소속·상태·권한 등)을 판정하는 로직을 작성하거나 발견하면, 코드베이스 내에 동일 개념을 판정하는 다른 위치가 있는지 검색한다(예: 같은 필드명·유사한 조건문 패턴). 이미 두 곳 이상에서 각자 판정하고 있다면, 하나의 공용 판정 함수로 통합하고 양쪽이 그 함수를 호출하게 만든다. 판정 기준은 개념당 하나만 존재해야 한다.

**발견 경위**: 2026-07-31, 스키마 변경 후 한쪽 화면에서만 소속 표시가 깨진 것을 조사하며 두 개의 판정 로직을 발견한 세션.

### 5. CJK 폰트 없는 검증 하네스가 텍스트 폭을 조용히 틀리게 잰다

**증상**: 일본어 UI 버튼의 텍스트가 실제 브라우저에서는 개행되는데, Playwright 하네스로 재면 "한 줄에 들어간다"고 나왔다. 폰트 크기를 12px→10px로 줄이는 판단의 근거 수치(4글자 × 12px = 48px)와 하네스 실측(28.81px)이 정면으로 어긋났다.

**원인**: 헤드리스 환경에 일본어 폰트가 하나도 설치돼 있지 않았다(`fc-list :lang=ja` = 0). CJK 글자가 .notdef(두부) 글리프로 폴백되면서 전각 1em(12px)이 아니라 0.6em(7.2px)으로 렌더됐다. 즉 하네스는 "전혀 다른 글리프의 폭"을 재고 있었다.

**왜 코드 리뷰로 못 잡는가**: 측정 스크립트도 앱 코드도 정상이다. 문제는 실행 환경의 폰트 유무이며, 스크립트는 오류 없이 그럴듯한 숫자를 반환한다. 게다가 이 오차는 "더 좁게" 나오는 방향이라 개행·오버플로 판정을 **거짓 PASS** 쪽으로 밀어낸다. FAIL이면 조사를 유발하지만 PASS는 조사를 멈추게 하므로 발견되지 않는다.

**회피법**: 비라틴 문자(CJK·태국어·아랍어 등)의 레이아웃을 하네스로 측정하기 전에 `fc-list :lang=<코드> | wc -l` 로 폰트 존재를 먼저 확인한다. 0이면 측정값을 일절 신뢰하지 않는다. WSL이면 `cp /mnt/c/Windows/Fonts/{YuGothR,YuGothM,YuGothB,meiryo,msgothic}.ttc ~/.local/share/fonts/win-ja/ && fc-cache -f` 로 해결되며, 사용자 브라우저와 같은 서체이므로 오히려 정확해진다. 검산: `あ` 를 12px로 재서 약 12px이면 정상, 7px대면 폴백이다. 관련 원칙: [02-verifying.md#6-검증-통과-시-확인할-것](./02-verifying.md#6-검증-통과-시-확인할-것).

**발견 경위**: 2026-08-01, `リセット` 버튼 개행 수정 중 사용자 보고와 하네스 실측이 어긋나 폰트 목록을 확인한 세션.

### 6. CSS 특이도 때문에 새 클래스가 먹지 않는데 검사 항목이 통과로 보인다

**증상**: `.zoom-controls-reset { font-size: 10px; white-space: nowrap }` 를 넣고 "개행 없음(`lineBoxes: 1`)"을 확인해 통과로 판정했다. 실제로는 폰트가 18px 그대로였고 텍스트가 44px 박스를 72px로 삐져나가 있었다.

**원인**: 기존 규칙 `.zoom-controls button`(특이도 0,1,1)이 신규 `.zoom-controls-reset`(0,1,0)을 이겼다. 두 선언 중 `white-space` 는 경쟁 규칙이 없어 적용되고 `font-size` 만 무시됐기 때문에, "개행이 사라졌다"는 결과만 보면 성공처럼 보인다.

**왜 코드 리뷰로 못 잡는가**: CSS 파일만 보면 의도한 값이 분명히 적혀 있다. 특이도 경쟁은 두 선택자를 함께 놓고 계산해야 보이는데, 통상 리뷰는 추가된 블록만 본다.

**회피법**: 스타일 변경을 검증할 때 "증상이 사라졌는가"가 아니라 **적용된 computed 값 자체**를 단언한다(`getComputedStyle(el).fontSize === '10px'`). 증상만 보면 부분 적용을 통과시킨다. 기존 파일에 `.<부모> <요소>` 형태의 규칙이 이미 있으면 신규 클래스는 같거나 높은 특이도(`.<부모> <요소>.<신규클래스>`)로 쓴다.

**발견 경위**: 2026-08-01, 줌 컨트롤 リセット 개행 수정을 실브라우저로 재검증하다 fontSize 를 함께 출력해 발견한 세션.

### 7. `tsc --noEmit` 이 파일을 0개 검사하고 조용히 통과한다

**증상**: 신규 Vite + TypeScript 프로젝트에서 `npx tsc --noEmit` 이 항상 에러 0건으로 통과했다. 실제로는 소스에 타입 오류가 있어도 잡히지 않았다. 「타입 체크 통과」를 완료 조건으로 삼고 있었으므로, 그 조건이 아무것도 보증하지 않는 상태로 여러 단계가 진행될 뻔했다.

**원인**: Vite 템플릿(create-vite)이 만드는 루트 `tsconfig.json` 이 solution 구성이다.

```json
{ "files": [], "references": [{ "path": "./tsconfig.app.json" }, { "path": "./tsconfig.node.json" }] }
```

`files: []` 이고 `include` 도 없으므로 이 설정이 지정하는 검사 대상은 **0개**다. `references` 는 `tsc -b`(빌드 모드)에서만 따라가지며, 일반 모드의 `tsc --noEmit` 은 참조를 무시한다. 결과적으로 "검사할 파일이 없어서 에러가 없다"를 "에러가 없다"로 읽게 된다.

**왜 코드 리뷰로 못 잡는가**: 명령도 정상이고 설정 파일도 템플릿이 준 정상 산출물이다. 출력이 아예 없어서(성공 시 무출력) 이상 신호도 없다. 게다가 이 결함은 **FAIL이 아니라 PASS 방향으로 틀리기 때문에** 조사를 유발하지 않는다. 5번·6번과 같은 계열이며, PASS 쪽이 더 위험하다는 원칙([02-verifying.md#6](./02-verifying.md#6-검증-통과-시-확인할-것))의 전형이다.

**회피법**: 타입 체크 명령을 완료 조건으로 채택하기 전에 **그 명령이 실제로 몇 개의 파일을 보는지 센다**.

```bash
tsc --noEmit -p tsconfig.json --listFiles | grep -v node_modules | grep -c "<프로젝트 src 경로>"
```

0이면 그 명령은 무의미하다. solution 구성이면 `tsc -b --noEmit` 을 쓰고, `package.json` 의 `typecheck` 스크립트에 그것을 박아 맨손 `tsc --noEmit` 이 쓰이지 않게 한다. 더 확실한 검산은 **고의로 타입 오류를 주입해 잡히는지 보는 것**이다(임시 파일에 하고 반드시 삭제).

주의: 명령을 다른 디렉터리에서 실행하면 `tsc` 가 cwd 기준으로 `tsconfig.json` 을 찾아 엉뚱한 결과를 낸다. 측정이 이상하면 [02-verifying.md#5](./02-verifying.md#5-검증-실패-시-의심-순서) 대로 **코드보다 먼저 측정 명령의 cwd·인자를 의심한다** — 실제로 이 세션에서 한 번 그 함정에 걸려 잘못된 FAIL을 냈다.

곁가지로 같은 템플릿에 `strict` 가 아예 없는 경우가 있다(create-vite 9에서 실측). `strict` 없이는 implicit any가 통과하므로, 타입 체크 명령을 고칠 때 `strict: true` 존재 여부도 함께 확인한다.

**발견 경위**: 2026-08-01, 포트폴리오 허브 repo 부트스트랩 중 워커가 고의 타입 오류 주입으로 발견해 보고했고, `--listFiles` 로 독립 재현한 세션.

### 8. 스크롤 연동 리빌 사이트를 헤드리스로 캡처하면 조용히 다른 화면이 찍힌다

**증상**: 작품 카드 썸네일용으로 데모 사이트를 Playwright로 캡처했더니, 히어로가 아니라 페이지 중간 섹션(`02 構築 / EXECUTION FLOW`)이 찍혔다. **이미지 자체는 깨끗해서 오류로 보이지 않았고**, 그대로 커밋했으면 "왜 이 화면이지?" 하고 나중에야 알아챘을 것이다.

**원인**: 두 가지가 겹쳤다. 첫째, 그 사이트는 로드 후 스스로 스크롤을 옮긴다(실측 `window.scrollY = 1483`). `window.scrollTo(0, 0)` 을 100ms 간격으로 12번 반복해도 계속 되돌려졌고, `document.documentElement.style.scrollBehavior = 'auto'` 로 스무스 스크롤을 죽여도 마찬가지였다. 둘째, 그래서 스크롤과 무관한 `screenshot({ fullPage: true, clip: { y: 0 } })` 로 페이지 좌표 상단을 잘라냈더니 이번엔 **완전히 빈 이미지**(6KB)가 나왔다 — 히어로가 스크롤 연동 리빌이라 그 시점에 `opacity: 0` 이었기 때문이다.

**왜 코드 리뷰로 못 잡는가**: 캡처 스크립트도 대상 사이트도 정상 동작한다. 오류·경고가 하나도 나지 않고 그럴듯한 JPEG가 생성된다. 판정하려면 **생성된 이미지를 사람이 열어봐야** 한다. 파일 크기(78KB → 6KB)가 유일한 기계적 신호였는데, 그것도 임계값을 미리 정해두지 않으면 보지 않는다.

**회피법**: 스크롤 연동 애니메이션이 있는 페이지를 캡처할 때는 **스크롤 위치와 싸우지 말고 `reducedMotion: 'reduce'` 로 컨텍스트를 만든다.** 리빌 구현 대부분이 `prefers-reduced-motion` 에서 요소를 `opacity: 1` 로 확정하므로, 자동 스크롤이 있어도 페이지 상단이 제대로 그려진다(`fullPage + clip` 과 조합하면 확실하다). 그리고 **캡처 결과는 반드시 이미지를 열어서 확인한다** — 스크립트의 종료 코드 0은 "찍혔다"를 뜻할 뿐 "맞는 화면이 찍혔다"를 뜻하지 않는다. 관련 원칙: [02-verifying.md#6](./02-verifying.md#6-검증-통과-시-확인할-것).

**발견 경위**: 2026-08-03, portfolio-hub 08단계에서 작품 카드 썸네일을 live 데모에서 캡처하다 이미지를 열어보고 발견한 세션.

### 9. `/mnt/c` の dev サーバーが古いコードを配り続け、検証が「落ちないテスト」になる

**증상**: 「古い保存レイアウトを読んでもクラッシュしないか」を確かめるハネスを書き、PASS を得た。念のため**修正を外して**再実行したところ、やはり PASS だった。つまりそのテストは欠陥を検出できていなかった。

**원인**: WSL の `/mnt/c` 上では Turbopack のファイル監視が取りこぼす。ソースを戻してもブラウザへ配られるのは**修正入りの古いバンドル**のままだった。ハネス側も、アプリ側も、どこにもエラーは出ない。

**왜 코드 리뷰로 못 잡는가**: 検証スクリプトもアプリコードも正しい。壊れているのは「今ブラウザで動いているコードが、今のソースと一致している」という**暗黙の前提**だけで、これはコードのどこにも書かれていない。しかも失敗方向が PASS なので調査が起動しない。

**회피법**: 受入検証は dev サーバーではなく **`npm run build` の成果物を静的配信して**走らせる(`python3 -m http.server --directory out`)。HMR の介在が無いので「配っているコード = さっきビルドしたソース」が保証される。
そして**新しく書いた検証は、必ず一度わざと落として検出力を確かめる** — 修正を外す / 期待値を反転させる、のどちらかで PASS→FAIL が動くことを見てから採用する。動かなければそのテストは無い。
関連: [02-verifying.md#6](./02-verifying.md#6-검증-통과-시-확인할-것)(PASS のほうが危険)、[#5](./02-verifying.md#5-검증-실패-시-의심-순서)。

**ポーリング設定では直らない(実測)**: 原因は inotify で、`/mnt/c` 上の `fs.watch` は変更2回に対しイベント **0件**(同条件の ext4 は2件)。ただし `next.config.mjs` の `watchOptions: { pollIntervalMs: 1000 }` を入れて dev を再起動しても復旧しなかった — ディスク上 `min-height:26px` に対し dev は `28px` を配り続け、75秒待っても再コンパイル0件。TSX の変更でも同じ(Next 16.2.12 + Turbopack)。設定値自体は `hot-reloader-turbopack.js` で Turbopack の watch に渡っているので、「渡っている＝効いている」と読まないこと。dev で見たいなら**サーバーを再起動**するしかない。

**발견 경위**: 2026-08-05, seatmap-demo に家具型を足し `SeatLayout.furniture` の既定値埋めを検証中、修正を外しても PASS が続いたため配信物を疑った。ポーリングが効かないことは 2026-08-08 に同リポジトリで実測。

### 10. 도구를 설치했더니 도구 자신이 사라진다 (npm 스테이징 잔여물이 재설치를 막는다)

**증상**: caveman 플러그인을 `npx -y github:...` 로 설치한 직후, `claude` 명령이 `No such file or directory` 로 사라졌다. nvm bin의 `claude` 심볼릭이 없어졌고, 패키지는 2.1.223 → **2.1.197로 되감겨** 있었으며 `bin/claude.exe` 는 290MB 네이티브 바이너리가 아니라 **500바이트 에러 스텁**이었다(네이티브 optional 의존성 미다운로드). 이미 실행 중이던 세션은 삭제된 inode를 물고 멀쩡히 살아 있어서, **세션 안에서는 아무 이상도 느껴지지 않았다.**

**원인**: 외부 설치 스크립트의 npm 작업과 Claude Code 자체 자동 업데이트가 겹쳤다. npm은 교체 시 기존 디렉터리를 `.claude-code-<해시>` 로 rename 해 두고 새로 푸는데, 그 스테이징 디렉터리가 남은 채 중단됐다. 이후 `npm install -g` 재시도는 **같은 이름으로 rename 하려다 `ENOTEMPTY` 로 계속 실패**한다 — 즉 잔여물이 스스로 복구를 막는 자물쇠가 된다.

**왜 코드 리뷰로 못 잡는가**: 코드 문제가 아니다. 설치 스크립트도 그 자체로는 성공(`EXIT=0`)을 반환했고 "done" 까지 찍었다. 게다가 **현재 세션은 계속 정상 동작**하므로(삭제된 실행 파일을 이미 메모리에 물고 있다) 다음에 새 세션을 열기 전까지 발견되지 않는다.

**회피법**:
1. 에이전트/CLI 도구에 외부 설치 스크립트를 돌렸으면, **끝난 뒤 그 CLI 자신이 아직 실행되는지 반드시 확인한다** — `command -v claude && claude --version`. 설치 스크립트의 종료 코드 0은 "다른 것을 안 망가뜨렸다"를 뜻하지 않는다.
2. 재설치가 `ENOTEMPTY: rename ... -> .../.<패키지>-<해시>` 로 실패하면 **코드가 아니라 스테이징 잔여물을 지운다**: `rm -rf <prefix>/lib/node_modules/@scope/.<패키지>-<해시>` 와 `<prefix>/bin/.<명령>-<해시>`. 지운 뒤 재설치하면 통과한다. 실행 중 프로세스가 그 디렉터리를 쓰고 있어도 Linux에서는 삭제가 안전하다(inode 유지).
3. 복구 확인은 심볼릭 존재가 아니라 **바이너리 크기**로 한다. 수백 MB가 아니라 수백 바이트면 그것은 스텁이며, 그 스텁도 `--version` 이 아닌 실행에서만 실패해 늦게 드러난다.

곁가지: 이때 `EBADENGINE` 로 `@anthropic-ai/claude-code@2.1.223 requires node >=22.0.0, current v20.20.2` 경고가 떴다. 경고일 뿐 설치는 되지만, 엔진 불일치 상태에서 자동 업데이트가 도는 것 자체가 이 사고의 배경일 수 있다.

**발견 경위**: 2026-08-06, Windows/WSL 설정을 WSL 하나로 통합한 뒤 caveman을 설치하고 발동 여부를 실측하려다 `claude` 가 통째로 사라진 것을 발견한 세션.

### 11. 삭제한 라우트가 검사 대상 목록에 남아, 검사가 조용히 공회전한다

**증상**: 접근성·오버플로 검사가 「4경로 PASS」로 보고됐지만, 그중 2경로는 이미 삭제된 라우트였다. 정적 서버에서는 5경로째에서 `waitForFunction` 이 30초 타임아웃해 **그 이후 경로가 한 번도 검사되지 않았고**, CI(`vite preview`)에서는 SPA 폴백이 200을 돌려주는 바람에 **NotFound 화면을 2번 검사하고 통과**했다. 어느 쪽도 「상세 페이지를 검사했다」는 사실이 아니다.

**원인**: 라우트를 지우는 커밋이 코드·`emit-routes` 까지는 정리했지만, 검사 스크립트의 `DEFAULT_PATHS` 와 워크플로의 인자 목록을 남겨뒀다. 정적 서버는 404(=`#root` 없음)를 주고, dev/preview 서버는 SPA 폴백으로 index.html을 준다 — **같은 목록이 실행 환경에 따라 다른 방식으로 틀린다.**

**왜 코드 리뷰로 못 잡는가**: 스크립트도 워크플로도 문법·의미 모두 정상이고, 목록에 적힌 경로는 「과거에 존재했던」 실재 경로다. 존재 여부는 목록을 읽어서는 알 수 없고 라우터 정의와 대조해야 보인다. 게다가 CI 쪽 실패 방향이 **PASS**라 조사가 시작되지 않는다.

**회피법**: 라우트를 삭제하는 커밋에서 **그 경로를 문자열로 들고 있는 곳을 전부 grep** 한다(`scripts/`·`.github/workflows/`·문서). 검사 스크립트는 「경로가 실제로 라우터에 있는가」를 먼저 단언하거나, 최소한 `#root` 미생성 시 타임아웃이 아니라 **명시적 FAIL** 로 떨어뜨린다. 그리고 검사 결과의 「N경로 PASS」를 볼 때 **N이 의도한 수와 같은지** 센다. 관련 원칙: [02-verifying.md#6](./02-verifying.md#6-검증-통과-시-확인할-것).

**발견 경위**: 2026-08-08, portfolio-hub 09단계 재디자인 검증 중 오버플로 검사가 4경로만 출력하고 죽는 것을 보고 목록을 확인한 세션.

### 12. `aria-hidden` 장식 텍스트도 색 대비 검사에 걸린다

**증상**: 카드 배경에 깐 큰 장식 문자(`opacity: 0.03`)가 axe의 `color-contrast` 위반 1.06:1로 나왔다. 요소에는 `aria-hidden="true"` 를 붙여 「지원 기술에서 숨겼으니 검사 대상 밖」이라고 생각하고 있었다.

**원인**: `aria-hidden` 은 접근성 트리에서만 숨긴다. **화면에는 그대로 보이므로** 색 대비 규칙은 계속 적용된다. 규칙이 보는 것은 「스크린리더가 읽는가」가 아니라 「사람 눈에 텍스트로 보이는가」다.

**왜 코드 리뷰로 못 잡는가**: JSX만 보면 `aria-hidden` 이 붙어 있어 오히려 꼼꼼해 보인다. 위반은 axe를 실제로 돌려야 나오고, 눈으로는 거의 안 보이는 요소라 화면 검토에서도 그냥 지나친다.

**회피법**: 정보를 갖지 않는 장식 문자는 요소로 두지 말고 **의사요소로 그린다** — `content: attr(data-glyph)` 처럼 데이터 속성으로 넘기면 시각은 그대로면서 axe의 검사 대상에서 빠진다(axe는 의사요소 텍스트를 평가하지 않는다). 대비를 3:1까지 올려 통과시키는 방향은 「장식」이라는 의도 자체를 깨므로 택하지 않는다.

**발견 경위**: 2026-08-08, portfolio-hub 09단계에서 배포 전 axe를 돌려 발견한 세션.

### 13. `overflow-wrap: anywhere` 가 `<wbr>` 의 문절 경계 우선순위를 무너뜨린다

**증상**: BudouX가 문절 경계에 넣은 `<wbr>` + `word-break: keep-all` 로 일본어 개행을 문절 단위로 고정한 뒤, flex 아이템이 min-content 아래로 안 줄어 생긴 横스크롤을 막으려고 그 요소만 `overflow-wrap: anywhere` 로 바꿨다. 오버플로는 사라졌지만 개행 품질이 오히려 나빠져, 「AIエージェント開発 / 環境(ハーネス)」처럼 **문절 중간에서 끊기는 사례가 새로 생겼다**(실측). `break-word` 로 되돌리면 사라진다.

**원인**: `break-word` 와 `anywhere` 는 사양 문구상 둘 다 "다른 개행 기회가 없을 때만" 임의 위치에서 끊는 것으로 읽히지만, 실제 Chromium 동작은 다르다. `anywhere` 는 min-content 폭 계산에까지 임의 개행을 반영하는 값이라 사실상 **모든 위치를 동등한 개행 기회로 만든다**. 그러면 greedy 줄채움이 「더 많이 채울 수 있는 임의 위치」를 골라, 앞쪽에 있는 `<wbr>` 경계를 지나쳐 버린다. `break-word` 는 min-content 폭을 바꾸지 않으므로 `<wbr>`·공백이 먼저 쓰이고, 그것들로 안 될 때만 발동한다.

**왜 코드 리뷰로 못 잡는가**: 두 값 모두 "넘칠 때 語中에서 折る"는 같은 설명으로 문서화돼 있어, CSS만 보면 강도 차이로만 읽힌다. 차이는 **min-content 폭에 반영되는가**이고, 그 결과는 렌더된 행을 실제로 뽑아 봐야 드러난다. 게다가 원래 고치려던 증상(횡스크롤)은 확실히 사라지므로, 그것만 확인하면 성공으로 보인다.

**회피법**: `<wbr>`·`keep-all` 로 개행 위치를 지정하는 설계에서는 **`overflow-wrap: anywhere` 를 쓰지 않는다**. 비상구는 `break-word` 로 둔다. flex/grid 아이템이 min-content 아래로 안 줄어 넘치는 경우는 `anywhere` 가 아니라 **그 아이템에 `min-width: 0`** 을 주거나, 애초에 넘칠 만큼 큰 글자 크기 쪽을 고친다(가변 `clamp()` 등). 그리고 개행 관련 CSS를 바꿨으면 "오버플로가 사라졌는가"가 아니라 **행별 문자열을 뽑아 앞뒤를 비교**한다.

**발견 경위**: 2026-08-09, J-paku.github.io 의 일본어 개행 고정 작업 중 카드 제목의 横스크롤을 고치다 개행 품질이 되레 나빠진 것을 하네스가 잡아낸 세션.

### 14. 측정 룰러의 `getComputedStyle().font` 가 빈 문자열이라 폭을 절반으로 재고도 조용히 통과한다

**증상**: 개행 검사 하네스가 "枠보다 긴 語라 어쩔 수 없는 개행"과 "피할 수 있었던 개행"을 나누기 위해, 숨긴 `<span>` 룰러에 대상 요소의 서체를 복사해 문절 폭을 쟀다. 결과가 계속 「불가피 0건」으로 나와 전부 진짜 결함으로 보고됐다. 실제로는 28px 서체의 문절 「AIエージェント開発環境」이 309px인데 룰러는 **158px**로 재고 있었다.

**원인**: 룰러에 `ruler.style.font = getComputedStyle(el).font` 로 서체를 넘겼는데, `font` 는 숏핸드라 `line-height`·`font-variant` 등 구성 프로퍼티가 숏핸드로 직렬화 불가능한 조합이면 **빈 문자열을 돌려준다**. 빈 문자열 대입은 무시되므로 룰러는 기본 서체(16px)로 측정한다. 28px 대상에 16px 룰러를 쓰면 폭이 약 6할로 나온다.

**왜 코드 리뷰로 못 잡는가**: 코드가 문법·의미 모두 정상이고 예외도 나지 않는다. 반환값이 그럴듯한 숫자라 이상 신호가 없다. 그리고 과소평가는 「문절이 틀에 들어간다」쪽, 즉 **PASS 방향으로 틀린다** — 03-pitfalls #5·#7과 같은 계열이다.

**회피법**: 텍스트 폭을 재는 룰러에는 `font` 숏핸드를 쓰지 않고 **`fontFamily`·`fontSize`·`fontWeight`·`fontStyle`·`fontStretch`·`fontFeatureSettings`·`letterSpacing`·`textTransform` 을 개별로 복사**한다. 그리고 룰러를 채용하기 전에 **검산 1개를 넣는다** — 알고 있는 문자열의 실측 폭(요소의 `getBoundingClientRect()`)과 룰러 값을 한 번 대조해, 크게 어긋나면 즉시 멈춘다. 관련 원칙: [02-verifying.md#6](./02-verifying.md#6-검증-통과-시-확인할-것).

**발견 경위**: 2026-08-09, J-paku.github.io 의 일본어 개행 하네스가 「문절 폭 158px < 틀 295px」인데 실제로는 줄바꿈이 일어나는 모순을 보고 룰러를 의심한 세션.

### 15. 헤드리스에서만 나는 페인트 어긋남을 앱 버그로 오진한다

**증상**: Playwright 헤드리스 스크린샷에서, 편집 모드에 들어가면 팀 라벨(인라인 `font-size: 72px` / `52px`)이 흰 라벨 판 밖으로 번져 좌석 그리드를 덮었다. 표시 모드는 정상. 두 모드의 차이는 편집 모드 진입 여부뿐이었다. 실제 브라우저에서는 **양쪽 모두 정상**이었다.

**원인**: 헤드리스(소프트웨어 렌더링) Chromium의 래스터/합성 경로 문제. 앱 쪽에는 원인이 없다. `EditSeatLayer` 가 `will-change: transform` + `transform: scale(0.65)` 레이어 안에 50개 넘는 형제 노드를 같은 React 커밋에서 동시 마운트하는 것과 상관관계는 있으나, 트리거를 분리하지 못했다.

**왜 코드 리뷰로 못 잡는가**: 코드에 결함이 없어서 소스로는 원리적으로 못 찾는다. 게다가 **DOM 프로브로도 안 잡힌다** — `getComputedStyle` · `getBoundingClientRect` · `elementsFromPoint`(복수 스택) · 조상 체인 전수 대조가 전부 두 모드에서 바이트 동일했다. 측정은 전부 "정상"을 가리키는데 스크린샷만 다르다. 실제로 이 사례에서 조사관 두 명이 DOM 실측만으로 원인을 찾다가 연달아 실패했다.

**회피법**: 하네스 스크린샷에서만 보이는 시각 이상은 **실기 재현을 확인하기 전에 앱 버그로 판정하지 않는다.** 판별 순서:
1. DOM 실측이 정상인데 스크린샷만 이상하다 → 렌더링 경로를 의심한다(반대로 DOM 실측이 이상하면 그건 진짜 앱 버그다)
2. 사용자에게 실기 확인을 요청하거나 headed / GPU 브라우저로 재캡처한다. `--headless=new` 는 headed와 같은 렌더링 경로라 중간 검증으로 쓸 수 있다
3. 실기에서 정상이면 하네스 아티팩트로 기록하고 코드를 건드리지 않는다

주의: 아래는 전부 시도해도 증상이 안 사라졌다 — 그러므로 "이걸 해도 안 없어지니 앱 버그다"라는 추론은 성립하지 않는다. 진행 중 transition/animation 정지(`reducedMotion` + `animations: 'disabled'`), `text-size-adjust: 100%`, `--blink-settings=textAutosizingEnabled=false`, `--disable-features=TextAutosizing`, `--force-device-scale-factor=1`, 강제 리플로우(뷰포트 리사이즈 왕복)·강제 리페인트, 대기 시간 연장(800ms까지).

관련 원칙: [02-verifying.md#4](./02-verifying.md#4-진단-충돌-처리)(측정으로 해소한다) — 단 이 부류는 **측정 대상 자체가 DOM이 아니라 페인트**라서, 측정 수단을 스크린샷+실기로 바꿔야 해소된다.

**발견 경위**: 2026-08-09, seatmap-demo 구조 부채 정리 라운드에서 CSS 모듈 오배선을 고친 뒤에도 남은 팀 라벨 과대를 조사하다, 사용자가 실기 확인으로 정상임을 알려 종결한 세션.

### 16. 에뮬레이션 터치는 브라우저의 제스처 강탈(pointercancel)을 재현하지 못한다

**증상**: 실기기에선 시트 본문을 아래로 끌어도 전혀 닫히지 않는데, CDP 터치 하네스는 dev·정적빌드·배포본 3환경 × 24케이스 전부 PASS. 사용자 보고와 하네스 실측이 정면 충돌했다.

**원인**: 배경 스크롤 가드(sheet-background-guard)가 「경로에 스크롤 가능한 요소가 있는가」를 용량(scrollHeight>clientHeight)만으로 판정해 네이티브 스크롤에 양보하고 있었다. 실기기 브라우저는 본문이 최상단이어도 세로 드래그를 스크롤로 선취해 pointercancel을 발화하고, 이후 pointerup/click이 오지 않아 스와이프가 시작조차 안 된다. CDP dispatchTouchEvent에는 이 선취 경로가 없어 하네스에서는 이벤트가 항상 끝까지 도달한다 — 즉 측정 도구 자체가 이 고장 모드를 볼 수 없었다.

**왜 코드 리뷰로 못 잡는가**: 코드도 하네스도 각각 정상이다. 갈라놓는 것은 브라우저 입력 파이프라인의 동작이라 소스 어디에도 없다. 게다가 하네스가 PASS 방향으로 틀리는 계열(#5·#7·#14와 동일)이라 조사가 자발적으로 시작되지 않는다.

**회피법**:
1. 「디스미스가 안 된다」류 보고는 수리 착수 전에 **제스처를 특정**한다(핸들탭 / 본문 스와이프 / ✕ / 배경 / Esc). 이번엔 사용자가 말한 것은 본문 스와이프였는데 핸들 스와이프부터 고치고 "완료"라 보고했다.
2. 하네스 PASS ↔ 실기기 FAIL 충돌 시 코드 재검토를 반복하지 말고, **사용자 브라우저에 진단 스니펫**(document capture 단계 pointerdown/up/click 로그 + elementFromPoint + buildId)을 심어 실측한다. pointerdown만 찍히고 up/click이 없으면 네이티브 강탈 확정. buildId로 「탭이 옛 번들을 물고 있는가」도 동시에 판별된다.
3. 터치 제스처 구현에서 네이티브 스크롤에 양보할지의 판단은 「스크롤 가능한 요소인가」가 아니라 「**그 방향으로 실제 스크롤 여지가 있는가**」(아래 드래그=scrollTop>1, 위 드래그=하단 여지)로 한다.

**발견 경위**: 2026-08-10, seatmap-demo 시트 스와이프 닫기 수리. 3환경 전 시나리오 PASS 후에도 사용자 실기기 재현이 계속돼, 진단 스니펫 로그(pointerdown 후 무음)로 원인을 확정한 세션.

### 17. SVG の data URI を数百要素の `background-image` にすると、再描画のたびに要素ごとの SVG 描画が走る

**증상**: ドット絵の村(20×18 マス+建物の正面、約 700 要素)で、町へ入った直後に押した方向キーが無視された。ja だけで、ko では起きない。E2E(Playwright)は ja の 1 件だけ 13 回中 12 回落ちた。

**원인**: 3 つが連鎖していた。(1) 町到着で出る案内文の漢字が Google Fonts の未取得サブセットを要求し、届いた瞬間に舞台全体の再描画が起きる(ko は既取得のサブセットで足りていたので起きない)。(2) スプライトシートが SVG の data URI で、`.sprite{background-image:url('data:image/svg+xml,…')}` を約 700 要素が共有していた。SVG 画像はビットマップと違い、**描画のたびに要素ごとに SVG 文書のライフサイクル(style/layout/paint)が走る**。トレースでは 1 回の Paint の中に `LocalFrameView::UpdateStyleAndLayout` が 694 回並び、244ms 掛かっていた。(3) 150ms のキー押下がその 244ms の中に収まり、keydown/keyup が同じ隙間に落ちて旋回すら起きなかった。

**왜 코드 리뷰로 못 잡는가**: CSS もコンポーネントも正しい。SVG シートは「1 枚を `background-position` で切り出す」という設計として妥当に見えるし、初回描画では 230ms が「町の読み込み」に紛れて気付かない。決め手は Chromium のトレース(`Paint` の中身と `ResourceSendRequest` の font/woff2)で、DOM 実測(`getComputedStyle`・`getBoundingClientRect`)には何も出ない。しかも症状は「たまにキーが効かない」で、再現条件(言語×書体キャッシュ×押下タイミング)が揃わないと出ない。

**회피법**:
1. 数百要素で共有する `background-image` に SVG の data URI を使わない。ピクセル単位の絵なら **PNG(`image-rendering: pixelated`)**にする。同じ絵を PNG に置き換えたら Paint は 198ms → 5ms 未満、data URI は 452KB → 3.4KB、HTML は 959KB → 62KB(スクリーンショット全画素一致)。
2. 「キー入力がたまに落ちる」「言語で挙動が違う」は主スレッドの停止を疑い、`PerformanceObserver('longtask')` と rAF の間隔で停止の時刻を取り、その時刻のトレース(`browser.startTracing` + `devtools.timeline`)で **Paint の中に何が何回あるか**を数える。JS プロファイルで `(program)` が支配的なら JS ではなく描画側。
3. E2E で入力を送る前は `document.fonts.ready` + rAF 2 回を待つ(書体到着の再描画を跨がない)。これは対症だが、遅いランナーで同型の落ち方をしないための保険として残す。
4. 「ローカルのフォント環境のせい」の仮説は `FONTCONFIG_FILE` で該当フォントを外して再実行し、1 回で潰す(今回は外しても 3/3 落ちた)。

**발견 경위**: 2026-09-18, J-paku.github.io の v2(Next.js App Router 移行)PR をローカルで CI 再現した際に E2E が ja だけ落ち、トレースで font/woff2 の到着直後の 244ms Paint を特定した。まず E2E 側の待ちで通し、その後「全部直して」の指示で SVG → PNG の根治に至った。

### 18. 같은 리포에서 두 세션이 동시에 일하면, 남의 미완성 코드가 내 커밋에 실려 나간다

**증상**: 낮·밤 기능을 워커 5명분 병합해 검증하던 중, 아직 커밋하지 않은 상태에서 다른 세션이 같은 리포에 커밋·푸시했다. 그 커밋(`5fcd9a1`)에는 **내 미검증 작업 전부 + 그쪽의 빌드 최적화**가 함께 들어갔고, 그 안에 한 번도 통과한 적 없는 E2E 4건이 섞여 있어 `main`의 CI가 실패했다. 내 쪽 터미널에서는 아무 신호도 없었다 — `git status`가 갑자기 깨끗해졌을 뿐이다.

곁가지로 같은 사고의 다른 얼굴이 하나 더 있었다: 고정 포트(4173)에 떠 있던 정적 서버가 **다른 세션의 빌드**였다. Playwright 설정이 `reuseExistingServer: true`라 그대로 재사용했고, 그 상태로 측정했으면 남의 산출물을 내 것으로 보고할 뻔했다.

**원인**: 작업 단위가 "워킹 트리"인데 그 트리를 두 주체가 공유했다. 커밋은 원자적이지만 **무엇을 커밋할지 고르는 일은 원자적이지 않다** — 한쪽이 `git add -A`/`git add .`로 전부 쓸어 담으면, 그 순간 트리에 있던 남의 중간 상태가 같이 들어간다. 커밋한 쪽은 자기가 무엇을 담았는지 모르고, 당한 쪽은 담겼다는 사실조차 모른다.

**왜 코드 리뷰로 못 잡는가**: 코드에 결함이 없다. 각 세션의 변경은 개별로 타당하고, 합쳐진 결과도 컴파일된다. 어긋난 것은 "이 트리의 미커밋 변경은 내 것"이라는 **암묵 전제**뿐이고, 그건 어느 파일에도 적혀 있지 않다. 게다가 실패가 원격 CI에서만 드러나므로 로컬은 끝까지 조용하다.

**회피법**:
1. **`git add -A` / `git add .` 를 쓰지 않는다.** 항상 경로를 명시해 스테이징한다(`git add <path> <path>`). 내가 만들지 않은 파일이 커밋에 들어갈 경로 자체를 없앤다.
2. 커밋 직전 `git status --short`를 읽고, **내가 손댄 기억이 없는 경로가 있으면 멈춘다.** 지우거나 되돌리지 말고 사용자에게 보고한다 — 그건 남의 진행 중 작업이다.
3. 커밋·푸시 전에 `git log origin/main..HEAD` 와 `git rev-parse HEAD origin/main` 로 **원격이 앞서 있지 않은지** 본다. 앞서 있으면 그 사이에 누가 밀어 넣은 것이므로, 내 것과 섞이기 전에 내용을 확인한다.
4. **고정 포트의 서버를 신뢰하지 않는다.** 측정 전에 `curl` 한 결과와 내 `out/index.html` 의 해시를 대조하고, 다르면 내 포트를 따로 띄운다(02-verifying #6 「검증 대상 확인」의 구체형).
5. 워커에게 주는 프롬프트의 `[Uncommitted Changes to Preserve]` 에 **다른 세션의 미커밋 파일까지** 넣는다. 워커는 트리를 공유하지 않지만, 회수 단계에서 내가 덮어쓸 수 있다.

**발견 경위**: 2026-09-20, J-paku.github.io 의 마을 낮·밤·날씨 작업. 회수·검증을 마치고 커밋하려는데 `git status` 가 2파일만 남아 있었고, `git log` 에 내가 만들지 않은 커밋이 있었다. 그 커밋의 CI는 이미 실패해 있었다.
