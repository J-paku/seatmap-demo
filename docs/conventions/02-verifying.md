# 02-verifying — "됐다" 고 말하기 전에 읽는다

수정이 끝나고 보고서를 쓰기 직전에 읽는다. 이 문서를 거치지 않고 "완료" · "동작 변경 없음" · "순수 이동" 이라고 쓰면 근거 없는 주장으로 취급된다.

## 1. 타입 체크로 못 잡는 것

`tsc --noEmit` 이나 Lint가 통과해도 다음은 별도 확인이 없으면 검출되지 않는다.

- **런타임 동작** — 타입은 "형태가 맞는 값"만 보장하지, "올바른 타이밍에 올바른 값이 오는가"는 보장하지 않는다
- **빌드 산출물** — 소스 코드와 배포물(번들·CSS 출력)이 일치한다는 보장은 없다 ([#2](#2-컴파일-결과를-봐야-하는-부류) 참조)
- **브라우저 API 실제 동작** — `ResizeObserver`·`matchMedia`·`IntersectionObserver` 등은 명세상 보장과 구현 의존적 세부(최초 통지 타이밍 등)가 별개다
- **이벤트 순서** — React 스케줄러 동작이나 effect 발동 순서는 타입 시스템의 관할 밖이다
- **캐시·영속 상태** — `localStorage`·`IndexedDB`·서비스워커 캐시에 남은 옛 데이터는 코드 변경과 무관하게 동작을 바꾼다

타입 체크는 이런 것들의 부재를 증명하지 않는다. "타입이 통과했다"는 "동작한다"를 대신하지 못한다.

## 2. 컴파일 결과를 봐야 하는 부류

소스는 정상인데 산출물만 다른 경우가 실재한다. 예: 빌드 도구가 벤더 프리픽스를 자동으로 붙이는 사양과 수동 작성한 표준 프로퍼티가 충돌해 표준 선언이 산출물에서 사라짐 (자세한 사례는 [03-pitfalls.md](./03-pitfalls.md) 해당 항목).

이 부류는 소스 리뷰로는 **원리적으로** 발견할 수 없다. 소스가 정상으로 보이기 때문이다.

확인 방법:
1. 빌드를 실행하고 산출물(`dist/`의 CSS/JS, `.next/static/` 등)을 직접 연다
2. 변경한 프로퍼티·선언이 산출물 안에 **그대로 존재하는지**를 문자열 수준에서 확인한다. 존재하지 않거나 예상과 다른 형태(다른 프리픽스로 치환됨 등)라면 의심한다
3. 실제 브라우저의 DevTools에서 computed style / Sources 탭으로 실제 배포되는 코드를 확인한다(소스맵 경유 표시가 아니라 배포된 원본 파일을 본다)

CSS·빌드 설정·번들러 동작을 건드린 변경은 소스 확인만으로 완료라고 부르지 않는다.

## 3. 개발자 환경에서 재현 안 되는 부류

새 세션·새 브라우저 프로필·시크릿 창 테스트만으로는 **영속 상태가 얽힌 버그를 영영 못 본다**. 이유: 새 환경에는 오염된 상태 자체가 존재하지 않기 때문이다.

예: `localStorage`의 목 캐시에 무효화 수단(버전·지문)이 없어, 데이터 스키마가 바뀐 뒤에도 옛 캐시를 계속 반환한 경우. 개발자가 새 브라우저에서 확인하는 한 재현되지 않는다.

재현 절차:
1. 대상 상태 원천(`localStorage`·`IndexedDB`·쿠키·서비스워커·캐시 헤더)을 찾아낸다
2. 변경 전 버전으로 한 번 앱을 조작해, 그 상태 원천에 **실제로 옛 데이터를 기록**한다
3. 그 상태를 유지한 채 새 코드로 전환해 같은 조작을 재시도한다
4. 시크릿 창이나 새 프로필 확인은 "최초 방문 시 동작 확인"이지 "마이그레이션 시 동작 확인"이 아님을 구분해서 쓴다

상태를 가지는 기능(캐시·영속 설정·스키마가 바뀔 수 있는 데이터)을 건드린 변경은 새 환경 테스트만으로 완료라고 부르지 않는다.

## 4. 진단 충돌 처리

**여기가 핵심이다.** 두 조사자(사람·에이전트 불문)가 상반된 결론을 냈을 때의 처리:

- **어느 쪽 결론도 채택하지 않는다**
- 자신감의 강도·설명의 길이·목소리 크기로 고르지 않는다. "더 자신 있게 말한 쪽"은 근거가 아니다
- **직접 측정한다.** 측정 수단이 없으면 측정 수단부터 만든다(로그 추가·실기기 확인·최소 재현 코드)
- 측정 결과가 나오기 전까지, 보고서에 양론을 병기할 수는 있어도 결론은 쓰지 않는다

○/×:

| 상황 | × Bad | ○ Good |
|---|---|---|
| 조사자 A는 "구조적으로 보장된다", 조사자 B는 "레이스 컨디션"이라 주장 | 더 상세히 설명한 A의 결론을 채택 | 실제로 브라우저에서 요소 크기를 실측해, 어느 쪽이 사실과 일치하는지 확인한 뒤 결론을 쓴다 |

진단이 갈리는 것은 대개 "실측하지 않은 전제를 양쪽 다 깔고 있기" 때문이다. 실측하면 충돌은 해소된다.

## 5. 검증 실패 시 의심 순서

검증 스크립트가 FAIL을 반환하면, **코드보다 먼저 검증 스크립트의 판정식을 의심한다**.

의심해야 할 전형적 지점:
- 반올림 오차(부동소수점 비교를 `===`로 하고 있는 등)
- 클램프 처리의 경계 조건(`min`/`max` 등호 누락)
- `computed style`의 문자열 형태(`"10px"`와 `10`의 비교, 단위 붙은 문자열 파싱 누락)
- 대기 시간 부족(비동기 처리·애니메이션·레이아웃 확정 전에 판정하고 있음)

왜 코드보다 먼저인가: 검증 스크립트는 대체로 코드 본체보다 새로 작성됐고, 리뷰를 거치지 않았으며, 실행 빈도가 낮다. "새롭고·리뷰되지 않았고·실행이 적은" 쪽일수록 결함 밀도가 높다는 것은 경험적으로 타당한 우선순위다.

코드와 스크립트 둘 다 의심스럽다면, 먼저 스크립트의 판정식을 최소 구성으로 단독 실행해 기대한 진위값을 반환하는지 확인한 뒤 코드 쪽을 의심한다.

## 6. 검증 통과 시 확인할 것

통과 신호는 그 자체로 근거가 아니다. "**무엇이 무엇을 통과했는가**"를 확인해야 근거가 된다. FAIL은 조사를 유발하지만 PASS는 조사를 멈추게 한다 — 그래서 PASS 쪽이 오히려 더 위험하다.

### 검증 대상 확인

스크립트를 돌리기 전에 그 스크립트가 실제로 무엇을 대상으로 하는지 확인한다. URL·경로·환경을 인자로 넘겼다면 **그 인자가 실제로 사용되는지** 코드를 본다.

예: Playwright 스크립트 10개가 `const BASE_URL = 'http://localhost:3100/'`로 하드코딩돼 있어, 배포본 URL을 인자로 넘겨도 무시하고 로컬을 검사했다. 전부 PASS가 나왔고 "배포본 검증 통과"라 보고했지만, 실제로는 배포본을 한 번도 보지 않았다.

### 보고와 실물 대조

다른 에이전트·워커의 "고쳤다" 보고는 파일 상태를 직접 확인하기 전까지 근거가 아니다. diff나 파일 내용을 직접 본다.

예: 워커가 "수정했다"고 보고했으나 파일은 그대로였다(본인도 나중에 "계획만 하고 쓰지 않았다"고 인정했다). 보고서만 읽고 다음 단계로 넘어갔다면 결함이 그대로 배포됐을 것이다.

### 샘플 통과 ≠ 현실 통과

직접 만든 픽스처·테스트 데이터는 작성자의 가정을 반영할 뿐, 판정 기준이 현실과 맞는지는 증명하지 않는다. 자동 검사 규칙을 만들었다면 기존 코드베이스 전체에 돌려 거짓 양성을 센다.

예: 자동 검사 규칙의 픽스처 6쌍은 전부 통과했지만, 실제 코드베이스 161개 파일에 돌리자 32개가 거짓 양성이었다.

○/×:

| 상황 | × Bad | ○ Good |
|---|---|---|
| 배포본 검증 스크립트가 전부 PASS | "배포본 검증 통과"라 보고 | 스크립트 소스에서 대상 URL이 인자로 실제 사용되는지 먼저 확인한다 |
| 다른 워커가 "수정 완료"라 보고 | 보고를 그대로 믿고 다음 단계로 진행 | 해당 파일을 직접 열어 diff로 변경 여부를 확인한다 |
| 자동 검사 규칙의 픽스처가 전부 통과 | 규칙을 그대로 배포 | 기존 코드베이스 전체에 돌려 거짓 양성 수를 센다 |

## 7. 보고 형식

"순수 이동" · "동작 변경 없음" 같은 **무해성 주장에는 반드시 원본 대조 근거를 붙인다**.

- "이동만 했다" → 이동 전후 diff에서 로직 라인에 차이가 없음을 실제로 제시한다(`git diff` 해당 범위를 보고서에 인용하는 등)
- "동작 변경 없음" → 변경 전후 동일 입력에 대한 출력이 일치함을 확인한 수단을 적는다(실행 결과·스크린샷·테스트 결과)

근거 없는 무해성 주장은 **검증되지 않은 것으로 취급한다**. "겉보기엔 안 바뀔 것"이라는 예측은 근거가 아니다.

예: `try` 블록의 범위를 "정리를 위해" 축소한 변경을 "순수 리팩터"라 보고했지만, 실제로는 예외를 잡던 라인이 블록 밖으로 나가 예외 방어가 축소돼 있었다. diff 대조를 했다면 발견할 수 있었다.

## 8. 완료의 정의

다음을 모두 만족했을 때만 "완료"라 부른다. 하나라도 빠지면 "미완료" 또는 "추가 검증 필요"로 보고한다.

- [ ] 변경이 요구된 동작을 만족하는지, 타입 체크가 아니라 **실행 결과**로 확인했다
- [ ] 빌드·번들 설정을 건드렸다면, 산출물을 직접 열어 확인했다 ([#2](#2-컴파일-결과를-봐야-하는-부류))
- [ ] 영속 상태·캐시를 건드렸다면, 옛 상태를 보유한 환경에서 재시도했다 ([#3](#3-개발자-환경에서-재현-안-되는-부류))
- [ ] 진단이 갈린 지점이 있었다면, 채택이 아니라 실측으로 해소했다 ([#4](#4-진단-충돌-처리))
- [ ] 통과 신호를 근거 없이 받아들이지 않았다 — 검증 대상·보고 실물·픽스처 대 실데이터를 확인했다 ([#6](#6-검증-통과-시-확인할-것))
- [ ] "무해" · "변경 없음" 주장에는 원본 대조 근거를 붙였다 ([#7](#7-보고-형식))
- [ ] 기존 자동 검증(타입 체크·Lint·테스트)을 실행하고 결과를 확인했다

이 항목들은 생략 가능한 체크리스트가 아니라, 해당하는 변경 카테고리에 걸리면 필수다.

## 9. 그래서, 검증 수단은 착수 전에 정한다

[8](#8-완료의-정의)의 체크리스트를 **일이 다 끝난 뒤에** 만족시키려 하면 늦다. 그 시점에는 "무엇을 보면 됐다고 알 수 있는가"를 새로 만들어야 하고, 만들기 귀찮으니까 결국 타입 체크로 때우게 된다. [1](#1-타입-체크로-못-잡는-것)이 반복되는 경로가 이것이다.

다단계 작업은 착수 전에 단계와 검증 수단을 **짝으로** 적는다.

```
1. {단계} → verify: {무엇을 보면 됐는지 아는가}
2. {단계} → verify: {…}
3. {단계} → verify: {…}
```

verify 칸이 안 채워지는 단계가 있으면, 그 단계는 아직 정의가 덜 된 것이다. "동작하게 만든다"는 검증 수단이 아니다.

| 약한 목표 | 검증 가능한 목표 |
|---|---|
| 유효성 검사 추가 | 잘못된 입력 3종을 넣어 각각 거부되는 것을 실행 결과로 확인한다 |
| 버그 수정 | 재현 절차를 **먼저** 적고, 그 절차가 수정 후 통과하는 것을 확인한다 |
| 리팩터 | 변경 전후 같은 입력에 대한 출력이 일치하는 것을 확인한다 |

테스트 프레임워크가 있으면 테스트가 그 수단이다. 없으면 만든다 — 실행 스크립트·실기기 확인·최소 재현 코드, **사람의 눈이 아닌 것**이면 무엇이든 된다.

단, 그렇게 새로 만든 검증 수단 자체가 결함 밀도가 가장 높다. FAIL이 나오면 [5](#5-검증-실패-시-의심-순서), PASS가 나오면 [6](#6-검증-통과-시-확인할-것)을 따른다.

### 9.1 UI 요소를 새로 두거나 옮길 때는 "살아야 하는 상태"를 착수 전에 캡처한다

새 버튼·띠·패널의 **위치**를 정하는 스펙은, 그 요소가 동작해야 하는 모든 화면 상태(모달 열림·지도 열림·가로/세로·터치/마우스)에서 **지금 빌드를 캡처해** 겹침을 눈으로 확인한 뒤에 확정한다. 확인 항목은 두 개뿐이다.

- 그 자리에 이미 무엇이 그려지는가(오버레이·고정 위치 요소·`z-index`)
- 그 자리의 색 토큰이 무슨 값인가(페이지 단위로 `--ink`/`--ground`를 뒤집어 두는 곳이 있다 — 토큰만 보고 고르면 극성이 반대로 나온다)

이유: 2026-09-18 J-paku A/B 버튼. 스펙은 "모달이 열려 있으면 A=다음, B=닫기"라고 적었지만 세로 모달이 `position: fixed; inset: 0`으로 조작 띠를 통째로 덮고 있었고, 페이지가 `--ground: #000`으로 뒤집어 둔 토큰 때문에 버튼 색이 반전됐다. 둘 다 착수 전 캡처 한 장이면 보였을 것을 구현 후 3라운드로 고쳤다. 코드를 읽어서는 안 보인다 — 겹침은 렌더된 결과에만 있다.

### 9.2 느린 검사는 반복 중엔 좁혀 돌리고, 전체는 마지막 한 번만

E2E·빌드처럼 1분 넘게 걸리는 검사는 수리 라운드마다 전체를 돌리지 않는다.

- 반복 중: **실패한 spec / 새로 만든 spec만** (`playwright test <file> -g '<이름>'`). 회귀 의심이 있으면 그 파일 하나까지
- 커밋 직전: 전체 1회. 이것이 유일한 전체 실행이다
- 전체 실행에서 새로 실패한 것이 있으면 그 spec만 좁혀 수리를 반복하고, 다시 전체 1회

이유: 2026-09-18, 3분짜리 E2E 전체를 라운드마다 돌려 3회. 실패 2건은 매번 같은 spec이었고 좁혀 돌렸으면 30초였다.
