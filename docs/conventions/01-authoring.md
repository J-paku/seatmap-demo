# 01-authoring — 파일을 만들거나 고칠 때 읽는다

새 파일을 어디에 둘지, 언제 쪼개고 승격할지 판단이 필요할 때 읽는다. 편집 **전** 판단을 위한 문서이며, 편집 후 검증은 [02-verifying.md](02-verifying.md)를 본다.

## 1. 배치 판단 플로우차트

위에서부터 순서대로 적용하고, **처음 걸린 곳**에 둔다. 기술 무관 원칙이며, 아래 그림은 프런트엔드를 예시로 든 것이다. 프로젝트 고유의 훅/컴포넌트 작성 규칙(`use` 접두사 세부, import alias 등)은 각 프로젝트의 `docs/authoring.md` 를 본다.

```mermaid
flowchart TD
    A[새 코드] --> B{JSX를 반환하는가}
    B -->|Yes| C[components/]
    B -->|No| D{Context + Provider인가}
    D -->|Yes| E[contexts/]
    D -->|No| F{"use"로 시작하며 React 기능을 호출하는가}
    F -->|Yes| G[hooks/]
    F -->|No| H{앱 밖(네트워크·영속 저장소·서드파티 SDK)과 통신하는가}
    H -->|Yes| I[lib/]
    H -->|No| J{타입 정의뿐인가}
    J -->|Yes| K[types/]
    J -->|No| L[순수함수·상수 → utils/]
```

이 순서인 이유: 위쪽 질문일수록 오판 시 피해가 크다. JSX를 utils에 두면 번들 경계가 깨지고, Context를 hooks에 묻으면 Provider 트리를 추적할 수 없다. 피해가 큰 판정부터 먼저 확정하고, 나머지는 소거법으로 utils에 떨어뜨린다.

## 2. `lib` 과 `utils` 의 경계

판정 기준은 하나뿐이다: **"앱이 죽어도 남는 쪽으로 나가는가"**.

- `lib/` — fetch·DB 클라이언트·인증·`localStorage`·`IndexedDB`·서드파티 SDK 호출. 앱 프로세스가 종료돼도 데이터나 세션이 외부에 남는다.
- `utils/` — 같은 입력에 같은 출력을 내는 순수함수·상수. 부수효과가 있더라도 그 부수효과가 **화면이라는 같은 세계 안에서 닫혀 있으면** utils 쪽이다.

DOM 실측·`matchMedia`·`element.style` 변경은 **"밖"이 아니다**. 이들은 현재 페이지가 닫히면 사라지는 일시적 부수효과이며, `fetch`나 `localStorage`처럼 앱을 넘어 영속하지 않는다.

| 예 | 배치 | 이유 |
|---|---|---|
| `fetch-mock.ts` (지연 포함 목 API) | `lib/` | 네트워크 경계를 모방 |
| `layout-persistence.ts` (localStorage 읽기/쓰기) | `lib/` | 영속 저장소 I/O |
| `geometry.ts` (좌표 변환 계산만) | `utils/` | 순수 계산, 외부에 손대지 않음 |
| `useElementSize.ts` (ResizeObserver로 DOM 실측) | `hooks/` | `use` 접두사이므로 hooks가 우선. lib/utils 둘 다 아님 |
| `matchMedia`로 브레이크포인트 판정하는 함수 | `utils/` | 페이지가 닫히면 사라지는 일시적 참조 |

○/×:

| 케이스 | × Bad | ○ Good | 이유 |
|---|---|---|---|
| 순수함수를 `lib/`에 둠 | `lib/format-date.ts` (날짜 포맷만) | `utils/format-date.ts` | I/O가 없다면 `lib/`를 봐도 아무것도 알 수 없다 |
| I/O를 `utils/`에 둠 | `utils/save-cache.ts` (내부에서 `localStorage.setItem`) | `lib/save-cache.ts` | `utils/`는 I/O가 없다는 전제가 깨지면 이후 모든 리뷰가 개별 확인 필수가 된다 |

`lib/` 에 순수함수를 섞지 않는다. `utils/` 에 fetch나 localStorage를 쓰지 않는다. 이 둘을 섞는 순간 "어디를 보면 I/O를 알 수 있는가"라는 불변조건이 무너지고, 이후 전체 리뷰가 개별 확인 필수 상태가 된다.

## 3. 쪼개기 판단 — 줄 수가 아니라 책임 개수

기준은 **줄 수가 아니라 책임 개수**다.

- 단일 책임이면 줄 수가 많아도 쪼개지 않는다. 쪼개면 호출부가 여러 파일을 오가야 해서 오히려 흩어져 추적하기 어려워진다.
- 책임이 둘 이상이면 줄 수가 짧아도 쪼갠다.

○/×:

| 케이스 | × Bad | ○ Good |
|---|---|---|
| 300줄짜리 단일 책임 훅 (상태 관리만) | "길다"는 이유로 `useX/` 폴더로 기계적 분할 | 그대로 한 파일로 유지 |
| 80줄짜리 파일이 순수함수와 훅을 동시에 export | 짧으니까 쪼개지 않음 | `utils/team-colors.ts` (순수함수)와 `hooks/use-team-color-map.ts` (훅)로 분리 |

책임이 함께 있는 전형적인 예: 한 파일이 "훅"과 "순수함수"를 동시에 export하는 경우. 이때는 책임별로 쪼개서 각자 본래 있어야 할 자리(`hooks/` / `utils/`)로 옮긴다. Context 파일이 날짜 계산 같은 순수함수까지 안고 있는 경우도 마찬가지로, 순수함수만 `utils/`로 빼낸다.

컴포넌트의 경우 **200줄을 넘고 책임이 여럿**이면 컴포넌트명 폴더로 쪼갠다. 단일 책무이면서 길기만 한 모듈은 쪼개지 않는다. 쪼개고 나서 입구를 어떻게 두는지는 [4](#4-폴더화했을-때의-입구), 파일명 규칙 같은 프로젝트 고유 세부는 각 프로젝트의 `docs/authoring.md` 를 본다.

## 4. 폴더화했을 때의 입구

쪼개기로 결정한 **다음**의 문제 — 폴더를 만들었을 때 바깥에서 무엇을 import 하는가. **컴포넌트와 훅은 답이 다르다.**

### 컴포넌트 — `index` 를 입구로 둔다

컴포넌트 폴더는 **공개물이 정확히 하나**다(그 컴포넌트 자신). 입구를 `index` 로 두면 호출부는 `@/components/AvatarCustomizer` 만 알면 되고 내부 구조를 몰라도 된다.

```
components/AvatarCustomizer/
  index.tsx       조립만. 로직은 전부 hooks/ 로 위임
  type.ts         타입은 평탄하게 여기에
  components/     전용 하위 부품
  hooks/          전용 훅
  utils/          전용 순수함수·상수
```

| | `index` 에 남는 것 |
|---|---|
| ○ | Props 수신, Context 읽기, early return, 하위 부품에 전달 |
| × | 상태 선언, 계산식, 분기 덩어리, 이벤트 핸들러 본체 |

× 쪽이 남아 있으면 쪼개기가 덜 끝난 것이다. 줄 수로는 **100줄을 넘어가면 의심**한다 — 조립만 하는 파일이 그 길이가 될 이유가 없다.

### 훅 — 폴더화해도 `index` 를 만들지 않는다

훅 하나가 여러 책임을 안게 돼 쪼갤 때는 **컴포넌트와 같은 모양으로 만들지 않는다.** `index` 를 두지 않고 **폴더명과 같은 이름의 훅 파일**을 입구로 삼는다. 호출부는 실제로 쓰는 훅을 파일 경로로 직접 지목한다.

| | 모양 | 호출부 |
|---|---|---|
| × Bad | `hooks/use-layout-editor/index.ts` | `from '@/hooks/use-layout-editor'` |
| ○ Good | `hooks/use-layout-editor/use-layout-editor.ts` | `from '@/hooks/use-layout-editor/use-layout-editor'` |

```
hooks/use-layout-editor/
  use-layout-editor.ts     묶는 입구. 아래 둘을 호출만 한다
  use-layout-draft.ts      편집 중 초안 상태
  use-layout-history.ts    undo/redo 스택
```

`index` 를 금지하는 이유:

1. **가리킬 "그 하나"가 없다.** 컴포넌트 폴더는 공개물이 하나지만 훅 폴더는 **동급인 훅의 모음**이다. 입구를 하나로 정하는 순간, 안쪽 한 개만 필요한 호출부가 갈 곳을 잃는다
2. **grep 이 끊긴다.** 배럴을 거치면 import 행에 실제 호출하는 훅 이름이 나오지 않아, `use-layout-history` 로 검색해도 호출부가 한 건도 걸리지 않는다. 훅은 호출부를 전부 찾아야 하는 일(의존 추적·삭제 판단)이 잦아서 이 손실이 크다
3. **부분 사용이 막힌다.** 묶은 입구만 필요한 화면과 안쪽 한 개만 필요한 화면이 섞이는데, 배럴은 전자만 허용한다

폴더명에도 훅 파일과 같은 명명 규칙을 유지한다(`use-` 접두사를 폴더에서 떼지 않는다). 떼면 `hooks/` 안에서 훅 폴더와 그 외 폴더를 이름만으로 구분할 수 없다.

## 5. 승격 기준

**2곳 이상이 쓰기 시작한 시점에**, 로컬(컴포넌트 전용 폴더 등)에서 루트 직속(`hooks/` `utils/` `lib/`)으로 끌어올린다.

이유: 복붙은 반드시 드리프트를 낳는다. 두 번째 사용처가 나타나는 순간이 복붙의 시작점이며, 그때 승격하지 않으면 세 번째 이후로는 "원본 사본"과 "고쳐진 쪽" 중 무엇이 정본인지 아무도 알 수 없게 된다.

○/×:

| 케이스 | × Bad | ○ Good |
|---|---|---|
| 두 번째 컴포넌트가 같은 날짜 포맷 로직을 필요로 함 | 컴포넌트 A의 `utils/format.ts`를 복사해 컴포넌트 B에도 만듦 | 루트 `utils/format.ts`로 승격하고, 두 컴포넌트 모두 `@/utils/format`으로 import |

로컬에 `lib/`는 만들지 않는다. 외부 접속은 앱 전체에서 한 곳으로 모아야 하므로 항상 루트 직속 `lib/`에 둔다.

## 6. 명명 규칙

파일명 규칙(kebab-case / camelCase / PascalCase) 자체는 프로젝트마다 달라도 된다. **최우선 사항은 "한 프로젝트 안에서 섞지 않는 것"** — 어떤 규칙이냐보다 규칙이 하나로 통일돼 있는 것이 더 중요하다. 신규 프로젝트에서는 기존 파일의 다수파를 따른다.

주의: 대소문자를 구분하지 않는 파일시스템(Windows·macOS)에서는 `useTeam.ts` → `use-team.ts` 같은 camelCase ⇔ kebab-case 리네임을 git이 **변경으로 인식하지 못할 수** 있다(대소문자만 다른 차이는 OS 쪽에서 동일 파일로 취급되기 때문). 리네임할 때는 일단 다른 이름을 경유하거나 `git mv --force` 상당의 조치를 취하고, 리네임이 실제로 스테이징됐는지 `git status`로 확인한다.

## 7. 고칠 때 건드리는 범위

여기까지는 "새로 만들 때"의 규칙이고, 이 절은 **기존 파일을 고칠 때**의 경계다. 판정 기준은 하나뿐이다: **바뀐 줄 하나하나가 요청까지 곧장 이어지는가.**

- 인접한 코드·주석·포매팅을 "겸사겸사" 고치지 않는다
- 망가지지 않은 것을 리팩터하지 않는다
- 기존 스타일을 따른다. 내 취향과 달라도 그 파일의 다수파를 따른다

삭제는 **내가 만든 고아만** 치운다.

| 대상 | 처리 |
|---|---|
| 내 변경 때문에 쓰이지 않게 된 import·변수·함수 | 지운다. 내가 만든 쓰레기다 |
| 원래부터 죽어 있던 코드 | 지우지 않는다. 보고서에 언급만 한다 |

이유: 관련 없는 변경이 섞이면 diff에서 "요청된 것"과 "덤"을 분리할 수 없게 되고, 리뷰어가 전부를 개별 확인해야 한다. 되돌릴 때 요청분만 되돌리는 것도 불가능해진다. 덤으로 넣은 개선이 사고를 냈을 때 원인 후보가 두 배가 되는 것은 덤이다.

○/×:

| 케이스 | × Bad | ○ Good |
|---|---|---|
| 함수를 고치다 같은 파일의 낡은 주석을 발견 | 겸사겸사 주석도 갱신 | 그대로 두고 보고서에 "이 주석은 낡았다"고 적는다 |
| 내 변경으로 `useMemo` import가 안 쓰이게 됨 | 남겨둔다 | 지운다 |
| 원래부터 아무도 안 쓰는 `legacyFormat()` 발견 | 정리하는 김에 삭제 | 지적만 하고 손대지 않는다 |

"고쳐두는 편이 낫다"는 판단이 서더라도 그건 **다음 요청거리**이지 이번 diff에 넣을 것이 아니다.

## 8. 이상적인 폴더 트리 예시

```
src/
  components/
    <Name>/
      index.tsx      # 조립만. 로직은 갖지 않는다
      type.ts         # 타입은 서브폴더를 만들지 않고 여기에 평탄하게
      components/     # 이 컴포넌트 전용 하위 부품
      hooks/          # 이 컴포넌트 전용 훅 (2곳 이상이 쓰면 루트 hooks/로 승격)
      utils/          # 이 컴포넌트 전용 순수함수·상수 (동일)
  contexts/           # Context + Provider
  hooks/              # 루트 공통 훅. `use` 접두사 필수
    use-x.ts          # 단일 책임이면 폴더로 만들지 않고 한 파일 그대로
    use-y/            # 쪼갤 때만 폴더화. index 는 두지 않는다 (4 참조)
      use-y.ts        # 묶는 입구. 폴더명과 같은 이름
      use-y-draft.ts  # 쪼개 나온 훅
  lib/                # 앱 외부와의 연결(fetch·DB·저장소 I/O·SDK)을 한 곳에 집약
  utils/              # 부수효과 없는 순수함수·상수
  types/              # 타입 정의만 있는 파일
```

`pages/` 같은 라우팅 파일은 정의 전용으로 두고, 화면 본체는 `components/<Name>/`에 둔다.

## 9. 색은 토큰 파일 한 곳에서만 정의한다

<a id="design-token"></a>

스타일시트에 색 리터럴(`#rrggbb` · `rgb()` · `hsl()`)을 직접 쓰지 않는다. 색의 정의 장소는 **토큰 파일 하나**(`tokens.css` 등)뿐이고, 나머지 파일은 `var(--color-...)`로만 참조한다.

이유: 리터럴로 쓰면 **테마를 바꿨을 때 그 부분만 옛 팔레트로 남는다.** 토큰은 테마별 블록에서 한 번에 갈리지만 리터럴은 갈리지 않기 때문이다. 그리고 이 어긋남은 기본 테마에서 개발하는 한 눈에 띄지 않아, 다른 테마로 실제 전환해 보기 전까지 발견되지 않는다.

- 반투명이 필요하면 `color-mix(in srgb, var(--color-surface) 97%, transparent)` 형태로 토큰을 희석한다
- **테마와 무관하게 고정하고 싶은 색도 토큰으로 만든다**(모달 암막 등). 「테마에 안 걸리니까 직접 써도 된다」는 예외를 열면 그 예외가 계속 늘어난다
- 색을 섞는 계산의 상대편도 토큰으로 둔다. 나중에 테마별로 조정할 이음매가 남는다

○/×:

| 케이스 | × Bad | ○ Good |
|---|---|---|
| 보조 텍스트 색 | `color: #6b7280` | `color: var(--color-text-muted)` |
| 모달 암막 | `background: rgba(0, 0, 0, 0.4)` | `background: var(--color-scrim)` (토큰은 전 테마 동일 값) |
| 반투명 배경 | `background: rgba(255, 252, 246, 0.97)` | `background: color-mix(in srgb, var(--color-surface) 97%, transparent)` |
